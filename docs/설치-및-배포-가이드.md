# 설치 및 배포 가이드

## 1. Supabase 준비

1. Supabase 프로젝트를 생성합니다. 가까운 리전(서울 권장)을 선택합니다.
2. SQL Editor에서 `supabase/schema.sql`을 실행합니다.
3. 기존 스키마를 보강하는 경우 `supabase/migrations/20260811_event_hardening.sql`을 검토 후 한 번 실행합니다.
4. Project URL, Publishable key, Secret key를 확인합니다.

SQL Editor가 영구 변경 여부를 묻는 것은 `CREATE`, `ALTER`, `DROP` 같은 DDL이 데이터베이스 구조를 실제로 변경하기 때문입니다. 이 저장소의 SQL을 대상 프로젝트에서 실행하는 경우 정상적인 확인 절차입니다.

## 2. 환경변수

`.env.example`을 `.env.local`로 복사하고 다음 값을 입력합니다.

| 이름 | 용도 | 노출 범위 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase 프로젝트 URL | 브라우저 공개 가능 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Publishable key | 브라우저 공개 가능, RLS 적용 |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버에서 DB 관리 작업 수행 | 서버 전용 비밀 |
| `ADMIN_PASSWORD` | `/admin` 로그인 | 서버 전용 비밀 |

`SUPABASE_SERVICE_ROLE_KEY`와 `ADMIN_PASSWORD`에는 절대 `NEXT_PUBLIC_` 접두사를 붙이지 마세요. `.env.local`은 Git에 커밋하지 않습니다.

## 3. 로컬 실행

```bash
npm ci
copy .env.example .env.local
npm run dev
```

- 참가자: `http://localhost:3000`
- 관리자: `http://localhost:3000/admin`
- 현재 결과: `http://localhost:3000/results`
- 전체 결과: `http://localhost:3000/final`

배포 전에는 `npm run lint`와 `npm run build`를 모두 통과하는지 확인합니다.

## 4. Vercel 배포

1. Vercel에서 이 GitHub 저장소를 Import합니다.
2. Framework Preset은 Next.js를 사용합니다.
3. 위의 환경변수 4개를 Production에 등록합니다.
4. Preview에서도 실제 데이터 흐름을 시험하려면 같은 변수를 Preview에도 등록합니다. Preview가 운영 DB를 변경할 수 있다는 점에 유의하세요.
5. 첫 배포 후 `/`, `/admin`, `/results`, `/final`을 점검합니다.

Git 연동 상태에서는 다음과 같이 동작합니다.

- `main` 이외 브랜치 푸시: Preview 배포
- `main` 푸시: Production 배포
- 이전 배포: Vercel Deployments에서 즉시 재배포하거나 롤백 가능

## 5. GitHub Actions

`.github/workflows/ci.yml`은 Pull Request와 `main` 푸시에서 다음을 검사합니다.

1. `npm ci`
2. `npm run lint`
3. `npm run build`

빌드에는 Supabase 공개 값과 형식상 유효한 서버 전용 테스트 값이 사용됩니다. 실제 운영 비밀은 GitHub Actions에 저장하지 않습니다.

## 6. 행사 당일 운영

1. `/admin`에 로그인합니다.
2. 실제 세션과 질문을 입력하고 휴대전화 2대 이상으로 투표와 집계를 점검합니다.
3. 실제 시작 직전에 `전체 투표 초기화`를 실행해 리허설 투표를 지웁니다.
4. `새 세션`은 질문을 복사하지 않으므로, 질문을 다시 입력할 때만 사용합니다.
5. 발표 장비에서 `/results`를 열고 F11로 전체 화면을 사용합니다.
6. 참가자에게 `/` 링크 또는 QR 코드를 공유합니다.
7. 질문별로 투표 시작과 종료를 진행합니다.
8. 마지막에는 `/final`을 열고 클릭·오른쪽 화살표·스페이스로 결과 슬라이드를 넘깁니다.

비개발자 담당자에게 전달할 상세 순서는 [행사 운영 시나리오](행사-운영-시나리오.md)를 참고하세요.

### 150명 투표 부하 테스트

행사 며칠 전, 실제 행사와 분리된 리허설 시간에 한 번 실행합니다.

1. 관리자 화면에서 리허설용 질문 하나를 `투표 시작` 상태로 만듭니다.
2. 프로젝트 폴더의 `.env.local` 값이 올바른지 확인합니다.
3. 프로젝트 폴더에서 `npm run load-test`를 실행합니다.
4. `성공: 150/150 (100.0%)`에 가깝고 p95 응답 시간이 3초 이내인지 확인합니다.
5. 끝나면 관리자 화면에서 `전체 투표 초기화`를 눌러 가상 투표를 지웁니다.

기본 테스트는 150명이 5초 동안 차례로 투표하는 상황입니다. 주소·인원·진입 시간을 바꾸려면 다음처럼 실행합니다.

```bash
npm run load-test -- --base-url=https://outreach-balance-game-live.vercel.app --users=150 --ramp-ms=5000
```

실제 투표 데이터가 생성되므로 행사 진행 중에는 실행하지 않습니다.

## 7. 배포 후 수정 확인

1. 새 브랜치에서 문구처럼 영향이 작은 변경을 커밋하고 푸시합니다.
2. Vercel Preview URL에서 변경 사항과 전체 투표 흐름을 확인합니다.
3. Pull Request의 CI가 통과한 뒤 `main`에 병합합니다.
4. Production 배포 완료 후 다시 핵심 경로를 확인합니다.
5. 문제가 있으면 Vercel Deployments에서 직전 정상 배포로 롤백합니다.

## 문제 해결

| 증상 | 확인할 내용 |
|---|---|
| 관리자 로그인 실패 | Vercel의 `ADMIN_PASSWORD` 값과 재배포 여부 |
| DB 요청 실패 | Project URL, Publishable key, Secret key의 프로젝트 일치 여부 |
| 참가자가 질문을 못 봄 | 현재 세션과 질문의 `active` 상태 |
| 배포 빌드 실패 | GitHub Actions 또는 Vercel 빌드 로그의 누락 환경변수 |
| 수정이 반영되지 않음 | 해당 커밋이 연결 브랜치에 푸시됐는지, 최신 Deployment가 Ready인지 |
